# Cloudflare 费用风险审计

## 1. 给非程序员的摘要

有几处会让任务重复运行、每日额度被多用，自动助手也可能把暂停的服务重新打开。  
先把处理结果放到另一个文件夹，阻止同一份文件被反复处理。  
再修好每日总额度，确保两个请求同时来时不会多放行。  
收好账户密钥，让自动助手只能查询和暂停，恢复交给你确认。  
提醒是否送达、实际用量、暂停能否生效，还没有证据。

## 5. 优先发现

### F-01 结果文件又被当成新文件处理，费用反复产生

**编号：** F-01

**标题：** 结果文件又被当成新文件处理，费用反复产生

**严重程度：** 高（High）

**所属层：** 第二层 代码限制

**规则编号：** L2-08、L2-12

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `src/worker.js:43–51`；`src/r2-consumer.js:4–7,9–44`；`config/r2-notifications.synthetic.json:5–12`；`wrangler.toml:43–48`。

**执行链：** 本项目的 scheduled 处理器写入固定输入；R2 的 `incoming/`、`.json` 创建通知进入队列；消费者读取输入后覆写 `incoming/DEMO_RESULT.json`，而该结果键也在 `INPUT_KEYS` 中并继续匹配通知过滤器，形成“输出→新通知→输出”的成功事件回路。增加的是 R2 读写、队列操作、Worker/DO 调用和额度存储操作，不能把新事件当成原消息的一次失败重试。[R2 官方说明](https://developers.cloudflare.com/r2/buckets/event-notifications/)确认覆写也触发 `object-create`。

**现有控制：** 输入最多 4096 字节，摘要截断为 64 字符；仅允许两个固定输入键，结果覆写固定键，不能据此推断对象数量无限增长。队列每批 1 条、并发 1、失败重试 2 次并有 DLQ。每轮先申请 2 份对象操作额度并检查开关，但这些限制没有让成功事件回路自然结束；额度可靠性见 F-02。

**最小修复：** 把结果写入不匹配输入通知的前缀，并从可处理键集合移除结果键；同时保留每个原始任务的处理上限。变更输出路径时要同步读取结果的调用方，避免遗留通知继续访问旧结果位置。

**验收证据：** 待补：在隔离事件替身中处理一次输入，确认最多一次所需结果写入，结果不产生下一条可处理通知；旧结果键的通知应被跳过。重复通知的处理另按 F-07 验收。

### F-02 两个请求同时进来，每日总额度可能被多用

**编号：** F-02

**标题：** 两个请求同时进来，每日总额度可能被多用

**严重程度：** 高（High）

**所属层：** 第二层 代码限制

**规则编号：** L2-05、L2-07

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `src/quota.js:3–14` 的 `reserveWorkUnits`；调用点为 `src/worker.js:44`、`src/r2-consumer.js:23`、`src/export-job.js:61`。

**执行链：** 报告、定时生产者及对象消费者共用项目/UTC 日期键，却分别执行 KV `get`、本地余额判断及 `put`。多个调用可能读取同一余额后覆盖对方的更新，使已获许可的对象操作多于记录值；旧缓存值还会造成低估。[KV 一致性说明](https://developers.cloudflare.com/kv/concepts/how-kv-works/)明确其最终一致性及不适合原子读改写的边界。

**现有控制：** 额度为每日 100 份 R2 操作准入单位；参数必须为正的安全整数，每个有费用的对象步骤前先检查额度，异常不主动放行，也没有失败后退款。队列单并发只限制该消费者，不能串行化报告和定时生产者；KV 写入频率限制也不能替代累计额度的正确记账。

**最小修复：** 让现有 ProjectControl 单例统一管理额度，把余额读取、校验和预留放入同一存储事务，所有入口共用；记录预留与任务的对应关系，退回预留额度前先确认它尚未被使用。代价是依赖该单例的可用性，故障时新对象工作需要等待。

**验收证据：** 待补：余额只剩 2 份时，让两个隔离调用各申请 2 份，应只成功一个；覆盖交错读写、旧值、跨入口及存储错误。成功预留总量与后续对象步骤应可对应，失败申请不得执行对象操作。

### F-03 账户密钥会被发给外部模型，权限也给得太多

**编号：** F-03

**标题：** 账户密钥会被发给外部模型，权限也给得太多

**严重程度：** 高（High）

**所属层：** 第四层 Agent 接管；第三层 自动暂停

**规则编号：** L3-11、L4-03、L4-09

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `planned-agent/plan.json:10–16` 的权限及凭证引用；`planned-agent/adapter.js:72–82` 的 `systemInstruction` 和 `agent.run`。凭证值不列入报告。

**执行链：** 拟议成本处置适配器将直接 Cloudflare 凭证和资源范围拼入系统指令并发送到模型端。计划范围为全部可访问账户，包含 Workers Scripts、KV、R2 和 Queues 写权限，扩大误操作和费用暴露面。不能把这些权限称作“仅暂停”；[删除 Worker 接口](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/delete/)接受 `Workers Scripts Write`。

**现有控制：** 应用运维令牌仅被适配器用于固定应用地址的 HTTP 请求，工具目的地址及名称也固定；但这没有阻止另一份直接 Cloudflare 凭证进入外部模型输入。

**最小修复：** 删除模型输入中的直接凭证，只让自有执行服务持有按项目和操作最小授权的凭证；模型仅获得调用受限查询/暂停接口所需的身份。代价是模型不能直接执行通用账户管理操作，额外操作须由所有者单独处理。

**验收证据：** 待补：审阅模型请求序列化结果和错误路径，确认没有直接密钥、认证头或原始客户内容；读取脱敏权限元数据，并用隔离拒绝记录证明跨项目及非允许操作不可达。

### F-04 自动助手可能把刚暂停的服务重新打开

**编号：** F-04

**标题：** 自动助手可能把刚暂停的服务重新打开

**严重程度：** 高（High）

**所属层：** 第四层 Agent 接管；第三层 自动暂停

**规则编号：** L3-10、L3-13、L4-02、L4-05、L4-06

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `planned-agent/adapter.js:4–18,55–94`；`src/worker.js:33–35`；`src/control.js:36–38`；`ops/pause-runbook.md:45–57`。

**执行链：** 当 `ruleTripped` 为真时，适配器先调用暂停；随后仍把 `resume_project` 暴露给模型，并按返回的工具名执行。恢复写入 `active=true`，可重新放行后续定时写入、队列对象步骤或新报告。它不会直接重启旧报告、恢复原生队列投递或重新配置计划，不能描述为一次性恢复全部资源。

**现有控制：** 确定的规则动作在模型预算和模型调用前执行，暂停失败会返回而不继续模型决策；工具目的地址及名字有固定列表。运维文档要求人工恢复，但实际工具集合允许模型撤销已经要求的停止，因而 L4-05 不能只凭执行顺序判为通过。持久存储本身有效，但 `active` 的重置路径及其所有权允许 Agent 绕过人工恢复要求，因此 L3-10 同样存在缺口。

**最小修复：** 从 Agent 的服务端操作集合移除恢复能力，并让恢复接口使用独立的人类运维身份和批准记录；仍允许模型给出恢复建议。复核预算、原因和积压后再恢复的运维流程继续保留，恢复速度会受到人工处理时间影响。

**验收证据：** 待补：隔离的 `ruleTripped=true` 事件必须在模型离线或超时时仍先执行暂停；即使模型明确选择恢复，也应被拒绝且停止状态不变。人类身份恢复只打开预定范围，并留下与停止事件对应的批准记录。

### F-05 告警里夹带的话，可能让自动助手做错事

**编号：** F-05

**标题：** 告警里夹带的话，可能让自动助手做错事

**严重程度：** 高（High）

**所属层：** 第四层 Agent 接管

**规则编号：** L4-04

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `planned-agent/plan.json:22–26` 的 signal 合同；`planned-agent/adapter.js:39–42,72–91`。

**执行链：** 经过账户/项目检查的 signal 仍包含外部提供的 `alertText`。该文字被截断后直接拼入系统指令，模型返回的工具只经过名称存在性检查便执行；包含操作指示的告警可能影响恢复等动作的选择。这里证明的是不可信文字进入高权限指令通道及缺少事件级动作授权，不能声称模型必然服从任何具体文字。

**现有控制：** 账户、项目及字段类型已检查，模型输入中的告警文字被限为 1200 字符，目的地址和三种工具名固定；告警不能直接指定任意账户、地址或任意工具。这些边界缩小影响，却不能让模型决定的动作自动符合当前停止策略。

**最小修复：** 将告警作为与系统指令分离的数据传入；由执行服务依据已认证事件、固定目标及规则状态校验允许操作，不让自然语言改变权限。结构化输入是辅助措施，不能代替服务端授权，也不能保证消除所有提示注入，参见 [Agent 安全建议](https://developers.openai.com/api/docs/guides/agent-builder-safety)。

**验收证据：** 待补：对带操作指示、错误项目及额外字段的隔离信号，确认目标不能被更换、事件禁止的动作不能执行；合法告警仍可产生被允许的查询或暂停。保留脱敏输入摘要与拒绝原因。

**严重程度：** 中（Medium）

**规则编号：** L2-08、L2-10

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `src/export-job.js:4–8,48–81` 的 `scheduleNext` 和 `alarm`；`src/control.js:7–8` 的固定报告标识。

**执行链：** 一次性报告失败后先构造 `retries+1`，但 `scheduleNext` 将该值重新保存为 0 并安排下一次 alarm，通常无法达到三次失败的结束条件。输入持续缺失会产生额外 R2 读取；额度存储持续报错时，即使没有新增 R2 操作，状态读取、记录写入及下一次调度仍会重复。应用新建 alarm 不受单个 alarm 的原生失败重试数约束，见[Alarms 说明](https://developers.cloudflare.com/durable-objects/api/alarms/)。

**现有控制：** 只有一个固定报告实例，约 30 秒后才重试；输入最多 4096 字节、结果摘要最多 128 字符。每次 R2 步骤前申请 2 份额度，额度不足会进入 `quota-held`，暂停也能阻止继续工作。因此并非无条件永远产生对象费用。等待未来 alarm 本身不能当成持续运行时长计费，见[DO 计费](https://developers.cloudflare.com/durable-objects/platform/pricing/)。

**最小修复：** 保留递增后的尝试状态，不在重新排期时清零；同一报告累计失败三次即转入终止状态，必要时另设任务截止时间。短暂故障超过三次后需要明确的新启动决定，不能自动复活原任务并恢复次数。

**验收证据：** 待补：隔离模拟三次连续输入缺失及三次额度存储异常，第三次后不再安排 alarm，状态为失败；成功完成、额度不足和暂停路径均不再自行排期。验收只使用本地替身和受控时钟。

### F-07 同一条通知再送一次，文件就可能多处理一次

**编号：** F-07

**标题：** 同一条通知再送一次，文件就可能多处理一次

**所属层：** 第二层 代码限制

**规则编号：** L2-09、L2-11

**判定：** 缺口（GAP）

**证据等级：** 源码（SOURCE）

**证据位置：** `src/r2-consumer.js:9–44`；`wrangler.toml:43–48`。

**执行链：** 每次收到允许的对象/版本通知都会重新申请额度、读取并写入结果，没有完成记录或原子处理权。重复投递，或 R2 写入已经成功但消息确认前中断，都可能产生重复的 R2 与队列费用；新输出还可能进入 F-01 的回路。Queues 提供[至少一次投递](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)，不能以业务处理完成推断不会重复收到。

**现有控制：** 消费者每批仅 1 条并逐消息显式 ack/retry；失败重试为 2 次并设置 DLQ，不存在未处理批次直接成功返回的暂停做法。原生失败重试有限，但不等于业务版本去重，也不能保证对象写入与队列确认同时完成。[批次与重试说明](https://developers.cloudflare.com/queues/configuration/batching-retries/)。

**最小修复：** 按账户、桶、对象及业务版本建立持久处理标识和受保护的处理中/完成状态；写入结果与本地确认之间结果不明时，核对目标结果后再决定重做。需要保存适当期限的去重记录，并增加故障后的核对步骤，不能承诺仅加一个键就得到恰好一次执行。

**验收证据：** 待补：同一对象版本的顺序及并发重复消息只产生一次必要结果；在结果写入后、ack 前模拟中断，恢复时先核对结果，不盲目重复收费步骤。仍应正确处理不同版本，不能为了去重丢掉新的工作。

### F-09 同一条告警反复送来，会重复花钱分析

**编号：** F-09

**标题：** 同一条告警反复送来，会重复花钱分析

**严重程度：** 低（Low）

**所属层：** 第四层 Agent 接管

**执行链：** signal 未要求稳定事件标识，也没有去重登记；同一告警重复交付会重新走确定性暂停、模型额度预留和处置记录写入。确定性暂停发生在模型预算检查之前，额度用完后单次交付仍可请求暂停和写记录；其累计量取决于尚未确定的宿主到达频率。这里可确认的重复模型工作受每日 20 次额度限制。

## 8. 下一步

1. **先把重复费用的入口关住。** 按 F-01/F-02 修复结果订阅和共享额度，再按 F-06 保存累计失败次数；验收应显示结果不再产生新处理、最后一份余额不会被多个任务同时使用、第三次失败后不再安排任务。
2. **收回自动助手不需要的权限。** 按 F-03–F-05 保留自有服务中的直接凭证，服务端仅开放指定项目查询/暂停，人工身份独立恢复；拒绝记录应证明告警文字和模型输出都不能改写停止决定。
3. **让重发只核对已有结果。** 按 F-07 和 F-09 保存对象版本及告警身份，区分完成、处理中和结果不明；验收同时覆盖一次成功后的重复交付与结果未知后的有界核对。
4. **把停止与恢复分开验证。** 按 F-08 明确清空定时计划，分别读取应用状态、计划、队列和有界新工作计数；恢复前核对原因、剩余预算、积压年龄和不确定结果，随后按既有并发限制逐步释放。
